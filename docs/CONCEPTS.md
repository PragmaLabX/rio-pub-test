# Разбор: GitHub Environment и настройки 2FA в Trusted Publisher

Два понятия, которые встретились при настройке pipeline — что это, зачем и
как это работает вместе.

---

## 1. Что такое GitHub Environment. 

**Environment** — это не облако, не сервер и не место, куда что-то
"физически" публикуется. Это **именованный набор правил доступа** внутри
самого репозитория GitHub, к которому job в workflow может быть привязан
строкой:

```yaml
jobs:
  publish:
    environment: npm-release   # ← вот эта привязка
```

Как только job ссылается на `environment: npm-release`, GitHub перед
запуском этого job проверяет правила, настроенные для `npm-release”
(Settings репозитория → Environments → npm-release). Если правил нет —
job просто выполняется, как будто environment не было. Если правила есть —
job **встаёт на паузу**, пока правила не выполнены.

### Зачем это нужно именно нам

У нас уже есть Trusted Publisher (OIDC) — он решает вопрос "может ли *эта
именно* GitHub Actions job вообще опубликовать *этот именно* npm-пакет"
(технический уровень доверия между системами). Environment решает другой
вопрос: **"разрешаем ли мы конкретно сейчас запустить публикацию"**
(человеческий уровень контроля) — это как заводской конвейер: OIDC — это
пропуск на территорию завода, Environment — это охранник у конкретного
цеха, который должен нажать кнопку, прежде чем станок включится.

### Правила, которые можно повесить на Environment

Настраиваются в Settings → Environments → `npm-release`:

| Правило | Что делает |
|---|---|
| **Required reviewers** | Job замирает и ждёт, пока один из указанных людей вручную не нажмёт Approve в интерфейсе GitHub. Без этого — job не пойдёт дальше, даже если тег уже запушен. |
| **Wait timer** | Просто пауза N минут перед стартом job (окно, чтобы успеть остановить релиз). |
| **Deployment branches and tags** | Список веток/тегов, из которых вообще разрешено запускать job с этим environment. У нас релиз идёт из тега `v*.*.*`, а не из ветки — **это надо явно указать**, иначе GitHub заблокирует job с ошибкой вида "branch/tag not allowed to deploy to this environment", потому что по умолчанию политика допускает только ветки. |
| **Environment secrets** | Секреты, видимые только job с этим environment (у нас не используются, т.к. авторизация через OIDC, а не токен). |

### Как это стыкуется с полем "Environment name" на npm

На странице Trusted Publisher (npmjs.com) есть необязательное поле
**Environment name**. Если его заполнить (у нас — `npm-release`), OIDC-токен,
который GitHub Actions присылает в npm, будет содержать claim с именем
environment, и npm сверит его с тем, что указано в настройках. Это ещё один
слой защиты: даже если бы кто-то скопировал наш `publish.yml` в другой
workflow с тем же именем файла, но без явной привязки к environment
`npm-release`, npm бы отклонил публикацию — имена не совпадут.

**Итого**: у нас должно совпасть 3 места — имя environment в
`publish.yml` (`environment: npm-release`), в GitHub Settings → Environments
и в поле "Environment name" на странице Trusted Publisher на npm. Если хоть
одно из трёх не создано/не совпадает — либо job зависнет, либо npm отклонит
токен.

## 2. Настройки 2FA на странице Trusted Publisher

На npmjs.com при настройке Trusted Publisher вы видите блок:

> Requiring an additional authentication method adds another level of
> security for your package.
>
> - ○ Require two-factor authentication and disallow bypass 2fa tokens
>   (recommended)
> - ○ Require two-factor authentication or a granular access token with
>   bypass 2fa enabled

Это переключатель **не про OIDC/GitHub Actions** — автоматическая
публикация через Trusted Publisher этих настроек вообще не касается и
продолжит работать при любом выборе. Речь только о том, **что разрешено
человеку**, который попробует опубликовать этот же пакет вручную (`npm
publish` с ноутбука, как мы только что делали).

| Опция | Что разрешает | Риск |
|---|---|---|
| **Require 2FA, disallow bypass tokens (recommended)** | Ручной `npm publish` пройдёт только если у аккаунта включена 2FA (OTP/security key). Токены с флагом "Bypass 2FA" для публикации этого пакета не работают в принципе. | Минимальный — нет обходного пути мимо 2FA. |
| **Require 2FA or a bypass-2FA token** | Ручной `npm publish` пройдёт либо с 2FA, либо с granular-токеном, у которого стоит галочка "Bypass two-factor authentication" (это то, что мы обсуждали как запасной вариант несколько шагов назад). | Выше — если такой токен утечёт (например, из CI-секрета, .npmrc, истории shell), им можно опубликовать пакет вообще без 2FA. |

### Почему это безопасно выбирать "recommended", не боясь сломать pipeline

Именно потому что OIDC — отдельный, третий механизм аутентификации, не
токен и не сессия с паролем. Он не пытается "обойти" 2FA — он вообще не
проходит через эту проверку, так как npm доверяет не человеку с паролем, а
криптографически подписанному короткоживущему JWT от GitHub, который
подтверждает: "этот конкретный workflow в этом конкретном репозитории
сейчас реально выполняется". Поэтому даже самая строгая опция (первая)
никак не блокирует автоматическую публикацию по тегу — она блокирует
только альтернативные ручные пути мимо CI/CD, что нам и нужно для
корпоративного стандарта: единственный официальный способ опубликовать
пакет — это через pipeline, а не с чьего-то ноутбука.

**Рекомендация**: выбрать первую опцию — *"Require two-factor
authentication and disallow bypass 2fa tokens"*.

## 3. Что означает фраза "Establish a trust... using OpenID Connect (OIDC)"

Это заголовок самого шага настройки на npm, описывающий суть Trusted
Publisher целиком:

- **Trust** здесь — это не разовый пароль и не долгоживущий секрет, а
  **правило проверки**, которое вы один раз задаёте на стороне npm:
  "публикации от репозитория `PragmaLabX/rio-pub-test`, workflow-файла
  `publish.yml`, environment `npm-release` — доверяю".
- Дальше при каждом запуске `publish.yml` GitHub сам генерирует
  подписанный токен (OIDC ID token) с этими фактами внутри и передаёт его
  npm CLI.
- npm проверяет подпись (что токен реально от GitHub, не подделан) и
  сверяет содержимое токена с тем самым правилом. Совпало — публикация
  идёт. Не совпало — `403`.

Ключевое отличие от обычного npm-токена: здесь **нет секрета, который
можно украсть**. Токен генерируется заново на каждый запуск, живёт минуты
и годится только для этого одного запуска этого одного workflow. Именно
поэтому это считается более безопасным способом для CI/CD, чем хранить
`NPM_TOKEN` в GitHub Secrets.
